# ChatCodex Applet 初期設計

状態: 0.5.0の実装仕様。初期設計の作成日: 2026-10-25。初期設計は実装前にコミット済み。

第13節は将来構想であり、現在の実装仕様・利用可能な機能とは区別する。

## 1. 目的と範囲

AppDock内に小さなCodexチャットを置き、既存MCPによる設定操作をそのまま利用する。独自のAIエージェントや設定変更エンジンは作らず、チャットとモデル・思考量・承認モードの選択に集中する。

初期機能:

- テキストの送信、返答の途中表示、会話の継続。
- モデルと思考量、4つの承認モードの選択。
- 実行中の停止、新しいチャット。
- Codexが要求した質問・確認への返答、接続・失敗状態の表示。
- Enter／Ctrl+Enterの送信キー、通常／詳細の表示設定、独立した開発者向け通信ログ、開始時の操作指示と既存メモリ利用の設定。

初期範囲外:

- 会話履歴の一覧・検索・切替・復元、他クライアントの会話への接続。
- 添付、画像、音声、読み上げ、思考過程の表示、ツール詳細の専用画面。
- Codexの導入・更新・ログイン、APIキー入力、MCP接続先や操作許可の管理。
- リモートApp Server、Codex Cloudの作業環境、ローカルAIへの直接接続。
- プロンプト編集、独自の権限ルール編集、任意のサンドボックス設定、独自プラグイン機構。
- ElectronのLanguageModel APIへの依存、本体のCodex専用API追加。

## 2. 構成と本体への影響

通常の `node` Appletと固定のローカルHTMLページを使う。独立リポジトリ名は `Applet.ChatCodex.at365`、Applet ID案は `at365.chatcodex`、ページIDは `main` とする。

```mermaid
flowchart LR
  UI["Appletのチャット画面"] <-->|既存pageActions・変更通知| Backend["Node Applet"]
  Backend <-->|専用stdin/stdout| Codex["Codex App Server"]
  Codex -->|登録済みMCP| Host["AppDockの共通操作API"]
  Host --> Settings["設定・公開コマンド"]
```

本体は既存ページ表示、限定bridge、Storage、共通情報取得、MCPを提供する。Codex固有の通信、状態管理、モデル候補、確認要求はAppletが所有する。

manifestのcapabilityは `pages`、`storage`、`settings`、`appdock-api`。共通APIの使用は起動元の `system.getInfo` によるinstanceId取得に限定し、設定変更はCodexからMCPを使う。ホスト情報の取得には既存のApplet側read許可が必要。書込み許可をApplet用に追加する設計にはしない。

今回の実装では本体を変更しない。必要な本体機能が不足していてもApplet側を先に実装し、不足の根拠と影響を記録する。利用するページ通知・入力境界は[Appletページ](../../AppDock.at365/docs/applet-pages.md)、APIの公開範囲と許可は[共通API](../../AppDock.at365/docs/appdock-api.md)と[MCP](../../AppDock.at365/docs/automation.md)に従う。

## 3. 画面と操作

```text
[接続状態]                              [新しいチャット]
---------------------------------------------------------
会話
  入力した文章
  Codexの返答／簡潔な実行状態
  必要なときだけ質問・確認
---------------------------------------------------------
┌ メッセージ入力 ────────────────────────────────────┐
│ [承認モード ▼]           [モデル ▼] [思考量 ▼] [↑] │
└─────────────────────────────────────────────────────┘
```

- 返答はまずプレーンテキストで表示する。生成したHTMLやスクリプトは実行しない。
- 送信キーはCtrl+Enter（既定）／Enterから選び、開いている画面へ即時反映する。Ctrl+Enter設定ではEnterで改行、両設定ともShift+Enterで改行する。IME変換中（isComposing・compositionイベント・keyCode 229）のEnterは送信しない。空白だけの入力は送れない。
- 送信操作を受け付けるまで入力を保持する。受付後は入力欄を空にし、送信済みの文章を会話に置く。
- 実行は同時1件。実行中は送信ボタンを「停止」へ切り替え、モデル・思考量・新しいチャットを無効にする。次の文章の下書きは入力できる。
- 自動スクロールは会話末尾を見ているときだけ行い、過去の文章を読んでいる位置を奪わない。
- 「新しいチャット」は待機中にだけ使える。現在の画面と実行中メモリーを切り替える操作で、Codexに保存された過去の会話を削除しない。
- ページ／別ウィンドウの選択、非表示時の寿命、共通配色は既存ページ基盤に従う。表示先の独自管理は追加しない。

最初は1つの会話だけを表示する。ページの非表示・表示先変更では会話、入力、Codexプロセスを保持する。Appletの停止・再起動後は新しい会話から始める。

## 4. モデル・思考量・承認モード

`model/list` をページングして候補を取得する。非表示モデルを追加取得せず、モデル名や思考量の固定リストを正本にしない。選択に使う実行モデル識別子は返された `model`、表示名は `displayName` とし、UI用の `id` と混同しない。

1. 保存済みモデルが利用可能なら選択を復元する。
2. 保存がなければ、一覧の `isDefault` を使う。候補が一意に決まらない場合は未選択として選択を求める。
3. 思考量は、そのモデルの `supportedReasoningEfforts` の中から選ぶ。
4. 保存済み思考量が有効なら復元し、それ以外の初期値は有効な `defaultReasoningEffort`。一意に決まらない場合は選択を求める。
5. 思考量を指定できないモデルでは選択欄を非活性にし、要求から `effort` を省く。

モデルを手動で変えた際は、現在の思考量が新しいモデルでも有効なら保持し、無効なら新モデルの有効な既定値を選ぶ。利用できない保存済みモデルは勝手に別モデルへ変更せず、元の選択を示して選び直しを案内する。取得失敗時も架空の候補へ置き換えない。

思考量の既知コードには短い日本語ラベルを付ける。未知コードは返されたコードのまま表示し、一覧に含まれる有効値として扱う。モデル・思考量の選択はその組み合わせを一括検証して保存する。

送信開始時の選択を固定して `turn/start` の `model` と `effort` に渡す。実行中に変えず、Codex全体の `config.toml` は書き換えない。

### 承認モード

入力欄の下部に4モードのメニューを置く。既定は `inherit`（Codexの設定に従う）。`ask`（確認して実行）、`auto`（自動審査）、`full`（フルアクセス）だけを追加し、任意のポリシーJSONは受け付けない。

最初の `thread/start` は承認・sandboxを上書きせず、応答の `approvalPolicy`・`approvalsReviewer`・`sandbox` をその会話の継承値として保持する。以降は各 `turn/start` に固定したモードの設定を渡す。

| モード | approvalPolicy | approvalsReviewer | sandboxPolicy |
| --- | --- | --- | --- |
| inherit | 会話開始時の値 | 会話開始時の値 | 会話開始時の完全な値 |
| ask | on-request | user | workspaceWrite、追加書込先なし、ネットワーク許可なし |
| auto | on-request | auto_review | askと同じ |
| full | never | user | dangerFullAccess |

待機中の変更は次の送信から反映し、会話や下書きを破棄しない。実行中は変更を拒否する。継承へ戻すときも値を省略せず、開始時の設定を明示的に復元する。`config/value/write` 等は呼ばない。管理制限などによるRPC拒否は画面に示し、別モードへの変更や再送を行わない。端末ごとのCodex設定の相違は保持し、開発用端末の結果だけを別端末での承認成功と扱わない。

## 5. Codexの起動と通信

同じPCのCodex実行プログラムを使い、AppletごとにApp Serverを最大1つ所有する。Applet有効化だけでは起動せず、ページ初回表示時に接続する。ChatGPTのデスクトップ画面や既存の実行中チャットを操作する方式にはしない。

起動候補は既存の `codex` コマンドから解決する。Windowsの `.cmd` shimを実行ファイルとしてそのままspawnせず、認識した標準shimから実体を解決する。実体の存在と起動を検査し、未知のshim・壊れた参照・未導入は接続失敗として案内する。コマンド本文の評価、任意shell文字列、自動インストールは行わない。対応する配置は[利用条件](usage.md)を参照する。

起動は実体の絶対パス、引数配列 `["app-server", "--listen", "stdio://"]`、非表示ウィンドウ、専用pipeで行う。Applet自身のstdin/stdoutは本体とのRPC用なので共用しない。Node Applet由来の `ELECTRON_RUN_AS_NODE` はCodexの子環境から除く。

Codex CLIの別途導入を前提とし、ChatGPTアプリだけの導入は対応環境に含めない。Codex設定と認証は既存ユーザー環境を継承する。独自のCODEX_HOME、認証コピー、トークン保存、Codex設定への書込みを行わない。同じユーザー・同じCodexホストの既定設定は `~/.codex/config.toml` で共有されるが、環境変数・プロジェクト・プロファイル・起動時指定による相違を考慮し、Codexが読む設定と本体がMCP登録した設定が一致していることを前提とする。

作業ディレクトリはApplet配置フォルダーとし、任意のユーザープロジェクトは開かない。Codexの既存設定・信頼判定・組織ポリシーは継承モードで維持する。実行領域を広げる指定は、利用者が明示的にフルアクセスを選んだ会話の送信だけに適用する。

基本手順:

1. `initialize` → 応答確認 → `initialized`。実験APIは有効化しない。
2. `account/read` で認証状態、`model/list` で候補を確認する。
3. 最初の送信で `thread/start`。会話IDはAppletのメモリーだけに保持する。
4. `turn/start` に入力と選択したモデル・思考量を渡す。
5. 通知で途中表示・操作状態・確認要求を更新し、`turn/completed` で終了する。
6. 停止は `turn/interrupt`。受付と実際の終了を分け、終了通知まで「停止中」とする。

Codex wireは独自のJSON-RPC形式で、本体用JsonLinePeerの転用はしない。要求IDで応答を対応付け、通知とCodexからの要求を区別する。最終itemを確定値として採用し、同じitemの途中表示へ重複追加しない。

## 6. 本体とAppletの画面通信

既存 `window.appletPage.call('actions.invoke', ...)` とNodeの `onPageAction` を使う。Applet独自のページ操作案は次の7件だけとする。

| 操作 | 入力例・役割 |
| --- | --- |
| `chat.read` | generation / after。画面状態とカーソル以降の表示差分を取得 |
| `chat.connect` | generation。初回接続または失敗後の明示的な再接続を受け付ける |
| `chat.send` | generation / requestId / text。送信を受け付けてすぐ返す |
| `chat.select` | generation / model / effort。候補と組み合わせを検証して選択を保存 |
| `chat.approval` | generation / mode。4モードの固定IDを検証して選択を保存 |
| `chat.new` | generation。待機中に新しい会話へ切り替える |
| `chat.stop` | generation。現在の実行を停止 |
| `chat.respond` | generation / requestId / response。対応する質問・確認へ返答 |

引数は宣言したstring/number/booleanのみとする。思考量の指定なしは空文字を内部値へ変換する。質問への構造化回答は小さなJSON文字列で受け、Appletでその質問の型と選択肢に照合する。任意RPCのmethodやCodex要求全体を画面から渡せる入口にはしない。

送信・停止・返答は受付後すぐに戻し、長い生成をページRPC内で待たない。送信requestIdの重複は現在世代の直近128件まで元の受付結果を返す。結果不明の自動再送はしない。

更新時は `context.pages.notifyChanged('main')`、画面は `onChanged` で `chat.read` を呼ぶ。通知は合図であり、本文の保存先ではない。細かい返答は短い間隔でまとめる。画面は通知を購読してから初回取得し、未接続の初回表示なら `chat.connect` を1回呼ぶ。通知を取りこぼした場合もafterから差分を取得できるようにする。

世代は会話切替・再接続時に更新する。古い世代の送信・返答は拒否する。表示差分が回収済みならリセット要求と現行状態の先頭バッチを返し、後続はカーソルで分割取得する。復元対象は現在実行中の会話だけとし、Codexの過去履歴APIを初期実装に持ち込まない。

既存のRPC上限1MiB、ページ操作入力64K文字、通常タイムアウト15秒を維持する。入力本文はUTF-8で32KiBまで、差分応答はシリアライズ後256KiBまでに分割する。会話表示のメモリーは8MiBを目安に古い確定メッセージから回収し、省略を画面に示す。実行中メッセージ・未回答要求を削って進行不能にしない。

## 7. MCPと確認要求

設定操作は既存CodexのMCP機能へ任せる。ツール定義の変換、独自のツール実行ループ、MCPトークンの読取り・画面への転送をAppletに追加しない。

操作指示がオンの場合（既定）、起動元の `system.getInfo` で取得したinstanceIdを会話の初期指示へ渡し、CodexにはMCPの情報取得で対象一致を確認してから設定操作するよう指示する。対象が判別できない場合は操作を進めず、会話内で状況を説明する。MCP登録名の固定値や接頭辞で対象を推測しない。

初期指示には、設定変更は公開MCPを使うこと、現在値・スキーマ・revisionを取得すること、必要なdryRunと実行後確認を行うこと、設定JSONを直接編集しないことを含める。具体的な操作契約は本体の[MCP仕様](../../AppDock.at365/docs/automation.md)を正本とする。

これはCodexへの動作方針であり、モデルに対する技術的な権限制限ではない。実際の操作許可はCodexの既存ポリシーと本体MCPが判定する。Appletはそれらを自動的に緩めない。

Codexからの対応済みの確認要求は会話内カードで表示する。要求ID、会話、実行、世代を照合し、提示された選択肢と回答型だけを返す。初期UIでは恒久的な許可ルールを編集せず、その要求に対する返答を扱う。タイムアウト、停止、新しい会話、`serverRequest/resolved` 後の古いカードは無効にする。

対応する要求methodと回答形式は採用Codex版のschemaに合わせる。未対応の要求を自動承認したり放置したりせず、その版で有効な拒否／未対応応答を返し、会話へ理由を表示する。実験的な質問APIのためだけに実験API全体を有効にしない。

## 8. 状態と終了

状態は `disconnected / connecting / idle / running / awaitingInput / stopping / error` に絞る。接続エラーは理由と再接続操作を会話欄に表示する。認証切れは既存Codexでのログインを案内し、自動ログインしない。

接続が失われた場合、処理が実行済みの可能性を残す。未完了の表示を「結果不明」で確定し、発言や操作を自動で再送しない。再接続は明示操作で行い、新しい会話から始める。

停止時は新規受付を閉じ、実行中turnの取消、未回答要求の解除、pipeの終了、所有する子プロセスの回収を行う。本体がdeactivateを最大2秒待つ契約に合わせ、無期限の終了待ちはしない。既存のCodexアプリや他のCodexプロセスを名前で一括終了しない。

Applet異常終了時に、App Serverがpipe切断で終了し子孫も残さないことを実機検証する。残存する場合はApplet所有の寿命管理手段を追加検討し、正常停止の成功だけで異常終了時も保証したと扱わない。本体への汎用プロセス管理API追加を先に前提にしない。

## 9. 保存・表示・ログ

共通Applet Settingsへ `sendKey`（ctrl-enter既定）、`chatDisplayMode`（inherit既定、inherit／normal／detail）、`wireLogEnabled`（false既定）、`sendOperationInstructions`（true既定）、`memoryMode`（inherit既定）を保存する。manifestと `src/chat-settings.cjs` のsettingDefaultsを揃える。表示設定はsettingKeysで内部のdisplayModeへ対応付け、inheritの場合だけ旧displayModeを読む。旧値がなければ通常、旧traceは詳細として扱う。normal／detailを明示した場合は新しい選択を優先する。inheritを保存上の既定にすることで、本体が既定値を省略しても明示したnormalが旧traceへ戻らない。新しい通信ログは明示的なwireLogEnabledだけで有効にする。旧キーはmanifestの選択肢検証の対象から外すことで、その値を消さずに新しいスイッチを保存できる。その他の未知値は読取り時に既定値として扱い、保存値を自動変換しない。Settingsの変更通知で送信キー・詳細・通信の各表示を即時反映する。開始時の2項目は最初のthread/startで固定し、途中の変更は「新しいチャット」から反映する旨を表示する。

操作指示がオフならApplet固有のdeveloperInstructionsを省略し、Codexの基底指示を置き換えない。メモリ設定のinheritは指定を省略し、include／excludeはthread/startのconfigへ `memories.use_memories: true/false` を渡す。メモリ機能そのもの・生成設定は継承し、config.tomlやメモリファイルへ書き込まない。自動注入の無効化はツールによるファイル読取りの禁止ではない。

詳細表示は自前の開始指示、送信設定、返されたinstructionSources一覧、公開ツールイベント、承認要求・回答を折りたたみ表示する。通信ログは要求IDで対応付けたJSON-RPCも表示する。Codex内部の最終指示やMEMORY_SUMMARY本文はAPIから返されない限り表示できない。任意のメモリファイルを別途読み込んで再現しない。

`src/diagnostics.cjs` で認証／設定RPC本文、未対応付けの応答本文、思考本文を除外し、秘密値キー・JSON文字列内の値・Bearer・URL資格情報を伏せる。各表示は16,000文字を目安に制限し、階層・件数にも上限を設ける。詳細と通信は独立して有効化し、オフにした種別の新規記録と表示だけを止める。通常表示でも通信ログだけを有効にできる。切替後に過去の通信は追加取得せず、保持済みの自前の開始情報だけ再表示できる。UIはtextContentを使い、HTMLを実行しない。診断はメモリーだけへ保持する。

保持枠は詳細・通信それぞれ本文のUTF-8サイズ512KiB／400カードを上限とする。超えたら、その種別の古いmessageIdに属する全パーツを回収して最新の記録を続ける。上限ごとの停止カードは追加せず、整理した種別の案内を会話欄に表示する。会話本文の8MiB枠とは分離し、診断の増加で会話・未回答要求・下書きを破棄しない。世代と会話IDも変更しない。

任意の位置の古いカードを回収するため、chat.readはmessage／detail／trace別の先頭orderをminOrdersへ返す。ページは種別ごとの位置より古いパーツをMapとDOMから除き、差分取得を続ける。全表示のリセットで回収を代用しない。新しいチャット・再接続では各保持枠と整理状態をリセットする。

PC専用Storageの1キー `preferences` に `{schemaVersion:1, model, effort, approvalMode}` を保存する。モデル候補、会話ID、本文、未送信入力、確認要求、会話開始時の承認設定はメモリーのみとする。approvalModeがない保存値はinheritとして読み、書き換えない。未知のモードは選び直すまで送信しない。破損・未知版は勝手に書き換えず、警告して明示的な選択保存で置き換える。

Appletが独自の会話履歴ファイルや認証ファイルを作ることはない。ただしCodex自身の会話保存はCodex設定に従うため、履歴が一切ディスクへ残らない機能とは説明しない。

UIの配色は本体の共通配色を使う。接続状態と最終失敗は会話内に表示し、安全な固定説明を既存context.log.errorで本体ログへ送る。共通エラー通知の公開API不足は[本体側の不足](host-gaps.md)へ記録し、本体は変更しない。本文・認証・生のRPC・生のstderrをログへ残さない。

## 10. 保守と実装時の構成

Codexの実行ファイル探索・通信は `src/codex-process.cjs`、会話状態は `src/chat.cjs`、承認モードの定義とAPI指定は `src/approval-modes.cjs`、Appletの寿命・ページ操作は `src/applet.cjs`、画面は `web/` へ分ける。依存と変換工程を減らすため、初期設計のTypeScript案から標準APIだけを使うCommonJS JavaScriptへ変更した。汎用プロバイダー層や拡張可能なチャット基盤を先に作らない。

Codexの対応版を実機で確認して明示し、その版から生成した型／schemaで必要部分を照合する。実験APIは使わず、無関係な通知の追加だけで失敗しない。必須の応答・要求形式が変わった場合は、互換性エラーとして案内する。

Codexの自動更新やインストーラーをAppletに組み込まない。新しい版をサポートする際は、会話、モデル・思考量、MCP、確認、停止を検証する。本体との既存契約が変わらなければApplet単独の更新で対応する。

manifest、ソース、dev.bat、publish.bat、必要試験をApplet内に置く。固定Nodeは隣の本体toolchain.jsonを参照する。最低ホスト版は0.86.13、初版は0.1.0。梱包は既存packerを使用し、本体を再ビルドしない。

## 13. 将来構想: Applet開発と作業再開（未実装）

2026-10-25に記録した将来の目標。以下は開発セットや再開機能の実装を開始する指示ではなく、今後の設計で考慮する要件と実装案である。通信ログの分離・上限回収は第9節の現行仕様として実装した。開発セット・会話再開の構想は未実装であり、以下の記述によって現在の保存仕様や再接続の動作を変更しない。

### 13.1 目指す操作の流れ

1. ボタン等からGitHub上のApplet開発セットをCloneする。セットにはAppDock本体、テンプレートApplet、必要な開発資料とビルド・インストール手順をまとめる。
2. ChatCodexでその開発セットをワークスペースとして選び、開発用チャットを開始する。
3. 「指定した機能を持つAppletを作成する」という自然言語の依頼を送る。
4. Codexがテンプレートを基に実装・必要な試験・ビルドを行い、指定したAppDockへAppletをインストールする。
5. AppDockを再起動すると、新しいAppletが利用できる。再起動後の検出・版・有効状態を確認して作業を完了する。

実装・ビルドの主体はCodexとし、ChatCodexが独自のコード生成エンジンを持つ構成にはしない。開発セットには対応するAppDock・SDK・テンプレート・固定ツールの組合せを明示し、繰り返し使える共通スクリプトへビルド・インストールをまとめる案とする。共通仕様は[Applet実装](../../AppDock.at365/docs/applet-development.md)と[設定・保存領域](../../AppDock.at365/docs/settings-sync.md)を参照し、本文を複製しない。

### 13.2 現在の実装から追加する部品

| 対象 | 現在の実装 | 将来の実装案 |
| --- | --- | --- |
| 作業場所 | Applet配置フォルダーで起動 | Cloneした開発セットを明示的に選択し、会話の作業場所へ指定する |
| 開始時の指示 | AppDock設定操作向けの指示を送る | 開発用の指示を分け、選んだワークスペースでのコード編集・試験・ビルドを扱う。AppDockの設定操作には既存MCPを使う方針を維持する |
| 開発環境 | Codex CLIは別途導入済みであることが前提 | Clone先、Git・Codex・対象Runtimeの固定ツール、開発セットの対応版を確認し、不足を具体的に案内する |
| インストール | ChatCodexに新規Appletのインストール機能はない | 生成したAppletのID・版・成果物・配置先AppDockを確定し、開発セットの共通手順で配置と結果確認を行う |
| 再開 | 会話IDはメモリーのみ。再接続・Applet再起動後は新しい会話 | 会話ID、作業場所、対象AppDock、工程と最後に確認できた結果をPC専用領域へ保存し、最後の開発作業を復元する |

初期案では履歴一覧・検索まで広げず、「この開発作業を再開」という最小限の入口を用意する。会話本文・認証・生の通信ログを独自に複製して履歴管理することは前提にしない。開発ソースの保存場所と、会話ID等の端末専用情報の保存場所は分ける。

API候補は `thread/start` の作業場所指定、`thread/resume`、`thread/compact/start`、`turn/start` の承認・実行領域指定。実装時に採用するCodex版の生成schemaと[公式App Server資料](https://learn.chatgpt.com/docs/app-server)を照合し、実接続で検証する。現在のChatCodexがこれらの再開・圧縮操作を実装済みであるとは扱わない。

### 13.3 中断後に続行できること

制限や失敗を一律の終了として扱わず、作業内容を保持し、原因・現在の状態・必要な次の操作を表示する。解消後は続行できる状態へ戻す。

| 中断・上限の種類 | 将来の扱い |
| --- | --- |
| 詳細表示・通信ログの上限 | 第9節の分離設定と保持枠・古いカードの回収を利用し、開発用チャットでも最新の記録を続ける |
| 長い依頼・大量の出力 | ファイル参照、分割取得、表示の省略等を使う。入力を黙って切り捨てず、通信の大きさと画面表示の管理を分ける |
| ファイル・ネットワークの権限不足 | 不足する操作と理由を示し、必要な承認や利用者によるモード変更の後に、同じ開発作業を続ける |
| 会話のコンテキスト上限 | 会話の圧縮で継続を試みる。復旧できない場合は作業要点と未完了工程を引き継ぐ方法を提示し、既存ファイルを保持する |
| 切断・AppDock再起動 | 保存した会話ID・作業場所・工程から復元し、現在のファイルや配置結果を確認してから残りを進める |
| Codexの利用枠・組織やOSの制限 | ChatCodexが制限そのものを解除できるとは説明しない。利用可能になる条件や必要な対応を表示し、解消後に再開できる状態を残す |
| ビルド・インストールの失敗 | 失敗した工程と結果を表示し、修正後は未完了の工程から続ける。結果不明の配置を自動で再実行しない |

「再開」は、会話とファイル・工程を引き継いで残りの作業を進めることを指す。中断したコマンドの実行位置や、承認待ちの要求をそのまま復活させることは保証しない。再接続後は完了済み・未完了・結果不明を区別し、古い承認カードや送信済み操作を再送しない。組織・OS・MCP側の権限を自動的に緩めず、選択した承認モードと現在の有効な制限を尊重する。

### 13.4 段階的な実装と確認事項

通信ログと通常の詳細表示の分離は第9節の現行仕様とする。今後の実装順の案は、(1)最後の会話の保存・再開と原因別の案内、(2)開発用ワークスペースと開始指示、(3)開発セットのClone・ビルド・インストール連携とする。順序・UI・保存形式は実装を依頼された段階で確定する。

今後決める事項:

- 開発セットのGitHubリポジトリ、対応版の固定方法、Clone先、既存フォルダーを選ぶ操作。
- AppDock本体の収録形式、テンプレートのRuntime、必要なツールの準備方法。
- インストール先の選択、同じApplet IDがある場合の扱い、再起動と再開の導線。
- 最後の開発作業を保持する期間、明示的な破棄操作、保存形式とCodex更新時の互換性。
- 既存Applet APIで実現できる範囲と、本体側の変更が必要になる場合の根拠・影響。本体変更を先に前提とせず、別途設計する。

受け入れ時は、隔離したAppDockで「Clone → 自然言語の依頼 → 実装・試験・ビルド → インストール → 再起動 → Applet検出と作業復元」を確認する。途中の権限待ち、通信ログ上限、ビルド失敗、切断、結果不明の配置も試験し、重複実行を起こさず未完了工程から続行できることを確認する。これらは将来の確認項目であり、現在の検証済み結果には含めない。
